# Qwen3.6 35B-A3B experiments

| Experiment | Decision / qualification |
| --- | --- |
| Prefill attention templated on head shape | Retained: the fast prefill kernel was previously compiled only for the Qwen3.8 27B head shape, so this 16Q/2KV `head_dim` 256 model silently fell back to baseline (301 t/s at pp8192) and hit an illegal-memory access at pp16384. Templating on the accepted head shapes restores the fast path. |
| Baseline prefill attention at ≥16K depth | Unresolved: the baseline prefill path crashes at 16384 and above and reproduces with any head shape absent from `detail/attention_policy.hpp`. Out of scope for this model; the accepted-shape fast path must be used instead. |
| MoE share of prefill | Before the attention templating, zeroing the expert output put routed + shared MoE at ~25% of prefill time at 8K depth. After it, per-stage event timing puts MoE at 52% of Q8_K_XL prefill at pp512 and 37% at pp4096 (43% for Q6_K_XL at pp4096); within it, the routed gate/up and down projections dominate. |
| Grouped BF16 expert GEMM (prefill) | Retained: the per-slot GEMV fallback made the 4 BF16 expert layers 29-33% of prefill time (48 ms/layer vs 5 ms/layer for Q8_0 layers at pp512). Grouping slots by expert and running a BF16 WMMA GEMM took Q8_K_XL prefill from 758/885/884 to 1208/1552/1605 t/s at pp512/2048/4096. Activations are rounded to BF16 (as llama.cpp does for BF16 weights); the op-test relative error against the FP32-activation GEMV is 0.13-0.18%. |
| Routed MMQ grid bound | Retained: capping the routed MMQ grid at the chunk's token count gives +7.6-10.1% prefill (Q8_K_XL pp512 1204→1295, pp4096 1601→1728; Q6_K_XL pp512 1221→1318, pp4096 1826→2010). Flash-Next's fitted column tile width on top was rejected: no gain at pp4096, unstable at pp512. |
| BF16 dense projections on the WMMA GEMM (MoE only) | Retained: UD-Q8_K_XL keeps layer 1's `attn_qkv`, `attn_gate` and shared expert in BF16, which the exact FP32-activation route ran at about 1 TFLOPS, doubling GDN input projection time versus UD-Q6_K_XL (22.7% vs 13.5% of a 4K prefill). Prefill chunks of >= 128 tokens now use the BF16 WMMA GEMM: interleaved A/B pp1024 1549 → 1753, pp4096 1716 → 2036, pp16384 1612 → 1872 t/s. Dense Qwen keeps the exact route because its cold/live continuation logits must match exactly. |
| Routed experts on the dense W8A8 WMMA kernel (grouped mode) | Rejected: slots grouped by expert into 16-token-aligned segments, gathered into the tiled Q8_1 layout and run through the dense prefill W-quant x A8 kernel with 32/64/128-token windows. Exact enough (0.4% RMS vs the FP32-activation GEMV, both quants pass the target test) but slower than the routed MMQ route: Q8_K_XL pp4096 2025 → 1744, pp16384 1875 → 1634; Q6_K_XL pp4096 1999 → 1800 t/s. The dense kernel's 29-45 TOPS on the GDN projections comes from reusing each weight tile across the whole chunk; an expert sees ~128 uneven rows at 4K, where its 128-row tiles and deep pipeline are mostly prologue and padding. Code kept outside the tree for reference. |
| Routed Q8_0 experts on Flash-Next's F16 expert GEMM | Retained: slots compacted by expert into 16-row padded buckets from per-expert counts read back once per layer, (expert, token tile) maps of 16 or 48 rows, F16 token rows, and the Flash-Next runner's F16 WMMA GEMM with in-kernel Q8_0 decode (gate, then up with SwiGLU to F16, then down to F16, F16 combine). Interleaved A/B on UD-Q8_K_XL: pp1024 1808 → 2033, pp2048 1966 → 2206, pp4096 2045 → 2251, pp16384 1886 → 2062 t/s; tg unchanged. The op test agrees with the FP32-activation GEMV to ~3e-4 relative (the int8 MMQ route was ~4e-3). UD-Q6_K_XL keeps MMQ (Q6_K gate/up is not decoded by that kernel). The kernels moved into `gufo_qwen38_flash_next_kernels` with unchanged compile flags; Flash-Next pp2048/tg16 is identical before and after. |
| Q6_K decode in the routed F16 expert GEMM | Retained: the kernel assembles each K block's 6-bit codes (ql nibble + qh bits) into bytes at fetch time and stages it like Q8_0, with a (d * scale) pair per 16-element half and the -32 code offset folded into the F16 magic constant (1056). UD-Q6_K_XL now takes the routed path in every layer. Interleaved A/B: pp512 1315 → 1775, pp1024 1694 → 2182, pp2048 1908 → 2384, pp4096 2019 → 2441, pp16384 1861 → 2217 t/s. The op test (random Q6_K blocks against the per-slot GEMV's independent Q6_K decode) agrees to ~4e-4 relative; UD-Q8_K_XL and Flash-Next are unchanged. |
| Routed down projection and mixed tiles on the paired map | Retained: `RoutedF16Gemm` accepts 128-row tiles, and a paired layer sends the expert down projection over the pair map instead of the 16/48-row map, so it decodes each expert's weights once per wide tile. The pair map is mixed: an expert with more than 64 padded rows gets 128-row tiles only, any other expert one 64-row tile, and gate/up and down each launch once per width. Giving one expert a 128-row tile plus a 64-row tail in a second launch was slower at pp4096/pp8192, so an expert's tiles stay in one launch. Interleaved A/B on UD-Q6_K_XL: down on the pair map pp2048 2575 → 2607, pp4096 2682 → 2723, pp8192 2592 → 2627 t/s; the mixed map on top pp1024 2276 → 2341, pp4096 2711 → 2723. Greedy completions on 6K and 12K prompts are byte-identical. |
| One-wave GDN post-norm, gate and quantize | Retained: for the 128-wide value dimension, one 32-thread block per (head, token) replaces the 128-thread block. Lane l holds elements l, 32 + l, 64 + l and 96 + l, so each register is one of the four groups the old kernel gave to a wave; the butterflies, the four-way sum and every per-element expression are unchanged and the block needs no LDS and no barrier. Output bytes equal the 128-thread kernel at 4096, 4070, 1024 and 37 tokens. Interleaved A/B on UD-Q6_K_XL: pp1024 2347 → 2387, pp2048 2629 → 2733, pp4096 2736 → 2826, pp8192 2631 → 2717 t/s, greedy output byte-identical. The isolated kernel only moves 0.85 → 0.73 ms; the model gains about 1 ms per layer, so kernels of this shape (one small block per token, barriers) have to be judged in the model. Other value dimensions keep the 128-thread kernel. Shared with the Qwen3.8 27B path. |
| Fused residual add, RMSNorm and Q8_1 quantize (hidden 2048) | Retained: one 256-thread block per token keeps its eight elements per thread in registers and writes the residual sum, the FP32 and BF16 normed rows and the tiled Q8_1 activation in one pass, at the GDN pre-layer norm and at the MoE FFN norm (which absorbs the post-attention residual add). The quantizer reads the BF16-rounded value, as the separate chain does, and the unrolled sum of squares keeps the generic loop's fused accumulation, so every output byte equals ResidualAdd → RMSNorm → QuantizeActivation at 4096, 4070, 1024 and 37 tokens. Isolated at 4096 tokens: 1.13 → 0.94 ms with the residual, 0.67 → 0.49 ms without. Interleaved A/B on UD-Q6_K_XL: pp4096 2830 → 2854, pp8192 2727 → 2740 t/s, pp1024/pp2048 unchanged within noise; greedy output byte-identical. A one-wave-per-row variant was exact but twice as slow. |
| Router and GDN alpha/beta on the BF16 WMMA GEMM | Retained for MoE prefill chunks of at least 128 tokens: the F32 router (hidden → experts) is rounded to BF16 for the WMMA GEMM, and the GDN alpha and beta matrices, adjacent in the weight storage, run as one stacked BF16 GEMM so the activations are read once. These projections are well under 1% of a chunk's arithmetic but took about a tenth of its time on the hipBLAS FP32 route. The one-row shared-expert gate, small chunks and dense Qwen keep that route. Interleaved A/B on UD-Q6_K_XL: pp1024 2525 → 2634, pp2048 2825 → 2984, pp4096 2991 → 3133, pp8192 2893 → 3029 t/s. Output is not byte-identical: greedy completions diverge from the FP32 route after tens of tokens, as paraphrases; see [Quality](QUALITY.md) for the checks that qualified it. A dedicated FP32 VALU GEMM (2 tokens x 16 rows per thread, sequential FMA chain) was rejected: the router ran in 1.05 ms against hipBLAS's 1.70 ms in isolation, but the model did not gain (pp4096 2722 → 2727 t/s) and greedy output changed anyway; about 25 tile layouts stayed at 2-4 TFLOPS. Stacking alpha and beta into one hipBLAS FP32 call gained nothing. |
| GDN `attn_qkv`/`attn_gate` on the dense F16 GEMM | Rejected: F16-narrowed activations through `DenseF16Gemm` instead of the int8 W-quant x A8 kernel gave +0.6% to +1.6% and changed greedy output. |
| Two-stream overlap of a dense GEMM and a bandwidth kernel | Rejected: a register-only WMMA loop and a DRAM copy do overlap fully when both grids leave wave slots free, but the production Q8_0 `attn_gate` GEMM beside the GDN convolution takes 0.99 of serial time as launched and at best 0.90 with token-sliced GEMM launches and a small-grid convolution, about 0.7% of prefill. |
| One-wave QK norm, RoPE and KV write | Retained: for 256-wide heads with a 64-wide rotary span, one 32-thread block per (head, token) replaces the 256-thread block. Lane l holds elements l + 32 * v, the rotary pair is lane p of registers 0 and 1, and the reduction is the same descending tree; each square and each normed value is kept as a separately rounded operand, as the LDS round trip left it, so Q, K and both KV cache representations are byte-identical at 4096, 4070, 1024 and 37 tokens. Isolated at 4096 tokens: 1.07 → 0.86-0.91 ms. Interleaved A/B on UD-Q6_K_XL: pp2048 2713 → 2746, pp4096 2858 → 2879, pp8192 2752 → 2769 t/s, pp1024 unchanged; greedy output byte-identical. Reading Q straight from the interleaved q/gate projection, so that only the gate is unpacked, was exact but gained nothing (pp4096 2886 → 2876) and was dropped. |
| GDN convolution in the qkv GEMM epilogue | Retained: on the row-split route the Q8_0 `attn_qkv` projection applies the causal convolution and SiLU in its own epilogue. A wave of the wave64 W-quant x A8 kernel owns four consecutive 16-token subtiles (a 64-token span), so the three earlier tokens of an output are in its LDS scratch or in the three rows it carries over from the previous subtile; tokens 3.. of a span go straight to the convolution output. The first three tokens of a span and its last four are written raw, and a small pass convolves the span heads (3 of 64 tokens) from them; the last four tokens of the batch are written raw for the convolution history. The projection and the convolution expression are unchanged, so the convolution output and the raw rows are byte-identical to GEMM followed by `BatchedSSMConvKernel` at 4096, 4070, 2017, 1024, 131, 128 and 96 tokens. A whole-span variant has no per-token bounds; chunks that are not a multiple of 64 take a guarded variant. Isolated at 4096 tokens: GEMM 5.23 ms, GEMM + convolution 6.35 ms, fused 5.33 ms (5.51 ms guarded at 4070). Interleaved A/B on UD-Q6_K_XL: pp1024 2433 → 2483, pp2048 2735 → 2808, pp4096 2881 → 2950, pp8192 2769 → 2840 t/s; greedy output byte-identical. Replay capture reads the raw projection, so capturing chunks keep the separate convolution. |
| DFlash2 block length from MoE verification cost | Retained: the adaptive length controller used the dense Qwen3.8 27B cost table (seven drafts cost 1.29x one draft). On this model a complete cycle costs 29.7/33.7/38.0/41.7/45.2/49.2/53.0 ms for 1-7 drafts, about 3.9 ms per extra row and 1.79x at seven, because routed experts are not shared between verified rows; a plain decode step is 18.0 ms. A lone request on an MoE target now uses those measured costs; cohorts of two or more requests keep the existing tables. Fixed-width sweep on UD-Q6_K_XL (greedy, 300 tokens, t/s for 1-7 drafts): prose 55.6/58.7/58.1/55.3/51.1/49.0/46.0, explanation 60.6/70.9/72.9/76.8/71.1/68.3/64.3, code 66.5/82.7/89.8/101.3/102.3/100.3/103.4, JSON 67.0/87.6/103.0/110.1/121.2/123.2/132.5. Adaptive with a limit of seven, before → after: prose 51.9 → 56.9 (plain decoding 55.7), explanation 65.8 → 73.2, code 102.8 → 103.4, JSON 132.5 → 126.0, the last from shorter blocks while the estimate ramps up on a 300-token run. The adaptive result is still 3-5% under the best fixed width on prose and explanation. |
| One launch for the per-row F32 GEMVs in verification | Retained: a verification batch ran the F32 projections (GDN alpha and beta, the MoE router, the shared-expert gate) as one `FastGEMVBlockKernel` launch per row, 24 launches per layer at six rows and about 113 us of wall time for 55 us of GPU work. The kernel now takes its input row from the grid and `LaunchGEMVRows` issues one launch per projection with the same per-row arithmetic; an eight-row cycle drops from about 1,825 to 1,073 kernels and completions are byte-identical at every block width. Interleaved A/B on UD-Q6_K_XL with DFlash2 (greedy, 300 tokens), fixed seven drafts: prose 45.8 → 48.4, code 103.2 → 108.2, explanation 64.2 → 67.2, JSON 132.2 → 138.3 t/s. The block-length costs above were re-measured on this build as 29.4/33.1/36.8/40.1/43.4/47.2/50.8 ms for 1-7 drafts (about 3.6 ms per extra row); adaptive with a limit of seven then gives prose 58.8, code 108.0, explanation 75.6, JSON 128.9 t/s. The dense verification GEMM was checked and left alone: it reads its weights at 190-212 GB/s, at the memory limit. A cycle remains bandwidth-bound: about 40 ms in the layers (routed experts 62%) and 11 ms after them, including two passes over the 540 MB vocabulary head. |
| DFlash2 context only for the draft's window | Retained: the draft attends to the last 2,048 positions, but every prefill step captured the eight target tap layers to the host and injected draft K/V for its last 2,048 tokens, which the next step overwrote; on a 12K prompt that was 2.7% of prefill. The request now passes the runner the next position at which the state is used (the next shared-prefix boundary, the prompt-cache snapshot position or the end of the prompt), and a step that ends more than one window before it runs without hidden capture while the draft only advances its position. Without a horizon nothing is skipped. While a skipped position is still inside the window the draft returns no proposal, in the single and the batched path, so a missed case decodes that step plainly. Greedy, DFlash2, UD-Q6_K_XL: prefill 12K 2740 → 2807, 24K 2530 → 2595, 6K 2848 → 2917, 11K 2828 → 2907 t/s; completions, cached-token counts and draft accepted/drafted counts are identical on long prompts, on a follow-up turn restored from cache and on repeated prompts, and three concurrent requests on a shared prefix give identical completions. The shared-prefix boundary case produced no cache hit in these runs and rests on the proposal guard. |
